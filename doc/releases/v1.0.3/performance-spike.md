# LetsMakeMoney v1.0.3 多窗口同步性能 Spike

## 结论

- Spike 状态：已完成。
- 证据状态：
  - 多窗口重复权威同步：已确认。
  - 窗口隐藏后继续执行权威同步：已确认。
  - 窗口隐藏后继续执行本地 1 秒 tick：高度可能。
  - 重复同步是 CPU 增量的主要来源：未确认。
  - 存在内存泄漏：未确认。
- 正式路由：
  - **隐藏窗口生命周期暂停/恢复**：进入 v1.0.3 PRD。
  - **共享快照或单一同步所有权**：不进入 v1.0.3 PRD，继续延期。

当前问题的最小边界不是“两个窗口必须共享一套全局状态”，而是 Tauri 隐藏窗口后，页面仍把自己视为可见，继续执行独立的 30 秒权威同步。应先关闭隐藏窗口的无效工作，再根据后续可归因数据决定是否需要共享架构。

## 测量方法

在相同应用、配置、设备与电源环境下，使用同一只读 PowerShell 采样器记录：

- 主进程和 WebView2 子进程累计 CPU；
- 工作集和私有内存；
- 进程与 WebView2 数量；
- 系统 CPU 平均值；
- `debug.log` 新增行数；
- `earnings.authoritative_sync.requested/completed/failed` 事件；
- 权威同步序列号。

窗口状态通过真实桌面操作建立：

1. 仅 Mini 可见；
2. Mini 与 Workbench 同时可见；
3. 关闭 Mini，使 Mini 隐藏、Workbench 可见；
4. 关闭 Workbench，使 Workbench 隐藏、Mini 可见。

Tauri 的关闭行为会阻止窗口销毁并执行 `window.hide()`，因此“仅一个窗口可见”的样本同时用于验证隐藏窗口的后台行为。

### 可重复事实

1. 未创建 Workbench 时，两个 10 分钟 Mini 样本均为 `21` 次请求和 `42` 行日志。
2. Workbench 创建后，10 分钟样本均为 `43` 次请求和 `86` 行日志，无论 Mini 或 Workbench 是否已经隐藏。
3. 双窗口相对真正单窗口的请求和日志倍率均约为：

```text
43 / 21 = 2.05
86 / 42 = 2.05
```

4. Mini 可见、Workbench 隐藏的 191 秒样本仍产生 `12` 次请求。日志中两套序列号交错：

```text
sequence=30, 4, 31, 5, 32, 6, 33, 7, 34, 8, 35, 9
```

序列 `30–35` 与 `4–9` 分别来自两个独立 `useDashboard()` 实例。这比仅比较请求总数更直接地证明隐藏窗口仍在执行自己的权威同步。

## 源码归因

### 独立同步所有者

- `MiniWindow` 调用一次 `useDashboard()`。
- `WorkbenchWindow` 再调用一次 `useDashboard()`。
- 每个 Hook 实例都创建独立的：
  - `requestSequence`；
  - 1 秒 `localTimer`；
  - 30 秒 `authorityTimer`；
  - 快照和错误状态。

### 可见性判断失效

`useDashboard()` 只使用 `document.visibilityState` 判断是否暂停：

- 本地 tick 在 `hidden` 时返回；
- 30 秒同步只在不是 `hidden` 时执行；
- 重新可见时执行一次权威同步。

原生层隐藏窗口时只调用 `window.hide()`：

- 通用隐藏路径记录 `window.hidden`；
- 关闭请求被拦截后调用 `window.hide()` 并记录 `window.close_hidden`；
- 没有向 WebView 发送对应的 `lmm:window-hidden` 事件。

原生层显示窗口时已有 `lmm:window-shown` 事件。实际测量证明，Tauri `hide()` 没有让当前 WebView 的 `document.visibilityState` 变为 `hidden`，所以现有前端守卫没有生效。

## CPU 与内存边界

同一 Mini 场景的两次样本总 CPU 分别为 `18.0312` 秒和 `0.8594` 秒，差异远高于窗口之间的稳定请求差异。当前采样无法把系统后台活动、WebView 暖机、React 渲染、1 秒 tick、日历计算和权威同步各自归因。

因此：

- 不将重复权威同步描述为已确认的主要 CPU 来源；
- 不使用当前 CPU 样本证明共享架构可降低 30% CPU；
- 不将工作集增长描述为内存泄漏；
- 不因资源数字不稳定否定已经由日志序列证明的重复同步。

## 共享所有权门禁

| 门禁 | 结果 | 说明 |
| --- | --- | --- |
| 双窗口请求/等价计算达到单窗口 1.5 倍 | 通过 | 请求与日志均约 2.05 倍 |
| 同步链路占双窗口 CPU 20% 以上，或存在真实状态竞态 | 未通过 | CPU 未能可靠归因，也未观察到状态竞态 |
| 受控原型 CPU 降低至少 30%，请求/日志降低至少 40% | 未通过 | 当前 Windows 环境缺少 Node、npm、Cargo 和 Rust 工具链，且本轮禁止修改业务代码，未构建原型 |
| 保留 1 秒显示节奏和最长 30 秒权威收敛 | 未验证 | 依赖原型 |
| 任意窗口开启、关闭、隐藏和恢复无单点失效 | 未验证 | 依赖原型 |

结论：共享快照或单一同步所有权没有满足既定实施门槛，不进入 v1.0.3 PRD。

## 进入 PRD 的最小修复

### 目标

隐藏窗口不执行本地 1 秒 tick 和 30 秒权威同步；窗口重新显示时立即获取一次权威快照，然后恢复正常节奏。

### 建议合同

1. 所有原生隐藏路径在隐藏前向对应 WebView 发送统一的 `lmm:window-hidden` 事件：
   - 显式隐藏命令；
   - 关闭请求转隐藏；
   - 首次配置期间隐藏 Mini；
   - 其他能保留 WebView 的隐藏路径。
2. `useDashboard()` 维护“原生窗口是否活跃”的本地生命周期状态。
3. 收到 `lmm:window-hidden` 后：
   - 暂停 1 秒本地 tick；
   - 暂停 30 秒权威同步；
   - 不清除最后一次可用快照；
   - 不把隐藏本身记录为业务错误。
4. 收到已有的 `lmm:window-shown` 后：
   - 重置 wall-clock/monotonic 基准；
   - 立即执行一次 `window_shown` 权威同步；
   - 恢复 1 秒与 30 秒节奏。
5. 配置在窗口隐藏期间发生变化时，隐藏窗口不立即计算；重新显示后的权威同步负责收敛。
6. 可增加低频语义事件：
   - `earnings.lifecycle.paused`
   - `earnings.lifecycle.resumed`
   - 禁止每秒写日志。

### 不做

- 不建立全局 React store；
- 不让一个窗口成为另一个窗口的单点数据服务；
- 不重写 Tauri 窗口架构；
- 不改变收入、日历、owner date、配置或错误合同；
- 不降低可见窗口的 1 秒金额展示节奏。

## 验收门禁

自动与真实桌面验证至少覆盖：

1. 仅 Mini 创建并可见，10 分钟权威同步约为单一 30 秒流。
2. 打开 Workbench 后出现两条可见窗口同步流。
3. 隐藏任一窗口后，连续 65 秒内被隐藏窗口不再产生 `interval_30s` 请求。
4. 重新显示窗口后，立即且仅执行一次 `window_shown` 权威同步。
5. 反复隐藏/显示 10 次，不出现重复 timer、序列乱序或同步永久停止。
6. 隐藏期间保留最后可用画面；重新显示后最长 30 秒内与权威结果一致。
7. 托盘隐藏/恢复、关闭转隐藏、首次配置和退出路径不回退。
8. 真实 Windows 睡眠/恢复与系统时间跳变通过。
9. 因 timer 生命周期发生变化，执行两小时稳定运行门禁。

推荐的量化通过标准：

- 一个可见窗口、另一个隐藏时，10 分钟请求和日志相对当前 `43/86` 至少降低到 `23/46` 以下；
- 预期目标为接近单窗口基线 `21/42`，请求与日志降低约 51%；
- 不将 CPU 降幅作为该最小修复的发布门禁，但继续采样并记录。
