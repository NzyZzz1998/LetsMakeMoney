# v1.0.3 官方年度日历数据维护

## 目的

本文定义 LetsMakeMoney 随应用离线分发的中国大陆官方节假日与调休数据如何新增、验证、发布和整组回滚。`manifest.json` 是支持年份、文件、数据版本和 SHA256 的唯一事实源。

本流程仅供仓库维护者在官方通知发布后使用。应用 v1.0.3 不提供在线下载、应用内导入或用户手工导入年度数据的能力。

## 权威来源

- 仅接受 `gov.cn` 及其子域名上的国务院办公厅正式通知。
- 每个年度文件必须记录发布机构、通知标题、文号、发布日期和原始 HTTPS 地址。
- 新闻转载、搜索摘要、社区整理、预测日历和往年规律不能作为官方年度文件来源。
- 2027 年官方通知尚未发布时，不得创建或预置 `cn-2027.json`，也不得把休息模式推算标记为官方数据。

## 新增年度

1. 从官方通知逐项录入法定节假日和调休工作日，文件命名为 `cn-YYYY.json`。
2. 保持 `schema_version: 1`，并令 `dataset_id` 与 `year` 一致。
3. 将年份按升序加入 `manifest.json` 的 `supported_years` 和 `datasets`。
4. 更新 `dataset_version`，计算年度文件 SHA256 并写入对应 manifest 条目。
5. 运行：

   ```powershell
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\verify_calendar_data_v103.ps1
   ```

6. 人工复核官方通知与 JSON 的日期集合、文号、标题和来源地址。
7. 从干净提交构建候选包，再运行包体验证；包内 manifest、年度文件和 SHA256 必须与源码一致。

## 自动门禁

校验必须拒绝：

- manifest 与年度文件集合不一致；
- 缺失或未知年度文件；
- 文件名、年份或 `dataset_id` 不一致；
- SHA256 不一致；
- 非 HTTPS 或不属于 `gov.cn` 的来源；
- 无效日期、跨年度日期或重复日期；
- `holidays[].dates` 与 `holiday_dates` 不一致；
- 同一天同时属于法定休息日和调休工作日；
- schema、字段或枚举不符合合同。

校验失败时不得构建候选包，不得改写上一份有效年度数据，也不得降级为“估算后冒充官方”。

## 整组回滚

年度数据、manifest 和对应验证证据作为一个不可分割的变更组回滚：

1. 停止该候选包的发布。
2. 恢复上一份已通过验证的 `manifest.json` 和全部 `cn-YYYY.json`。
3. 重新运行年度数据校验、聚合验证和包体验证。
4. 重新构建候选包并生成新的 Zip、EXE、DLL 和年度数据哈希。
5. 在 bugfix log 或发布文档中记录错误年度、触发原因、回滚提交和新候选身份。

不得只回滚 manifest 或只回滚单个年度文件；两者不一致必须被视为发布阻塞。

## v1.0.3 不变基线

v1.0.3 开发期间，2025 与 2026 年数据内容及 SHA256 保持不变：

| 文件 | SHA256 |
| --- | --- |
| `cn-2025.json` | `3C7911EEEEC200FFCD4C7C20ED84C64B06F23EC81818AD50D9EAEE88081C1280` |
| `cn-2026.json` | `440169EAD0FCDA71C15CBAAE11EC557DC0846EECA103A988D267303D9C306042` |

新增年度不需要修改 Rust 年份分支；构建期索引和发布包均由 manifest 动态枚举。
