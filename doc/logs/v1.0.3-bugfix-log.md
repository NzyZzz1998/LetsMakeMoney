# v1.0.3 Bugfix Log

## V103-BUG-001 隐藏 Workbench 后 WebView2 持续高 CPU

### 现象

最终候选连续运行预检中，Mini 保持可见、Workbench 创建后隐藏。Workbench 前端的 1 秒 tick 与 30 秒权威同步已经暂停，但进程树仍连续出现高 CPU：

- 预修复 120 分钟采样的最大单核占用为 `25.2921%`。
- 连续超过 `10%` 的最长区间为 28 分钟。
- 仅保留 Mini 时未复现；创建并隐藏 Workbench 后可稳定复现。
- 未发现权威同步错误或重复前端 timer，问题不属于共享状态架构。

### 根因

Tauri 的 `window.hide()` 和前端生命周期暂停只停止了应用 timer，没有暂停隐藏窗口的 WebView2 渲染器。直接调用 `ICoreWebView2_3::TrySuspend` 的第一版修复又被 WebView2 以 `0x8007139F` 拒绝，因为控制器在发起挂起前仍处于可见状态。

根因边界为：隐藏二级窗口的原生 WebView2 生命周期未与窗口显隐策略同步，不是收入计算、日历、配置事务或多窗口共享快照问题。

### 修复

- Windows 隐藏路径先调用 `ICoreWebView2Controller::SetIsVisible(false)`。
- 随后调用 `ICoreWebView2_3::TrySuspend`，并记录请求、完成及失败阶段。
- 恢复路径先调用 `Resume`，再调用 `SetIsVisible(true)`。
- 为 `webview2-com` 和 `windows-core` 固定兼容版本。
- 新增只读合同测试并接入 `scripts/verify_v103.ps1`。
- 不引入共享 Dashboard store、跨 WebView 快照广播或永久同步所有者。

  - `window.webview_suspend_completed detail=label=workbench suspended=true`
  - `window.webview_resume_completed detail=label=workbench`
- Mini 可见、Workbench 隐藏的 6 分钟受控复验：
  - 平均单核占用 `0.7808%`
  - 最大单核占用 `1.7368%`
  - 连续超过 `10%` 的采样数为 `0`
  - 私有内存变化 `-12,496,896` 字节
- 真实 GUI 连续 10 次显示/隐藏：
  - suspend requested/completed `10/10`
  - resume requested/completed `10/10`
  - lifecycle paused/resumed `10/10`
  - suspend/resume failed `0`
- 第十次隐藏后 75 秒内仅 Mini 保留 30 秒 timer，共产生 2 次 interval 同步，符合预期。
- v1.0.3 聚合验证通过：
  - 年度日历 `11/11`

  - 生命周期 `8/8`

  - v1.0-v1.0.2 历史回归通过

  - 连续运行 `7201.27` 秒，进程始终存活。
  - 15 分钟预热后平均单核 CPU `0.3302%`，最大 `2.8137%`，连续超过 `10%` 的样本为 `0`。
  - 私有内存增加 `4,108,288` 字节，工作集增加 `6,541,312` 字节。
